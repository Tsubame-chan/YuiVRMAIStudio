# 任意ローカルLLMの追加・外部サーバー接続：検討メモ

更新日：2026-10-11。**以下はコード調査に基づく提案であり、確定仕様・実装済み機能・対応保証ではない。** 実装前に利用者の需要、対応形式、各OSの実機結果、配布・保守コストを検討する。今回、任意モデル取り込みUIやOllama専用接続を実装したわけではない。

## 目指す機能

- 標準2B、任意追加4Bに加え、ユーザーのお気に入りのモデルを選べるようにする。
- モバイルでは、その端末で実際に動作する形式・メモリ・速度の範囲で追加モデルを導入できるようにする。
- Backendでは、PCやサーバーの能力に応じたモデルを選べるようにする。Backend自身が管理する実行環境、またはユーザーが立てたLLMサーバーへの接続を候補とする。
- 外部LLMサーバー → Yui Backend → デスクトップ／モバイルという経路でも、キャラクター・会話・音声の体験を維持する。

20B・30Bは会話中に挙がった例であり、対応目標・最低要件・最大サイズとして固定しない。総パラメータ数だけで導入可否や品質を判定しない。量子化、MoEの活性パラメータ、CPU/GPUへの分割・オフロードなどで実行条件が変わる。一方、活性パラメータが少ないことは、重み全体の保存容量や必要メモリも同じ割合で減ることを意味しない。対応エンジン、量子化方式、実ファイル容量、コンテキストとKVキャッシュ、利用可能メモリ、初回ロード、応答速度、発熱・電力を実測して判断する。

## 追加モデルの登録案

既存の `YuiLocalModelCatalog.cs` は、永続データの `YuiLocalAI/additional-models.json` を標準カタログへ統合する。モデルID・ファイル名の重複や標準モデルの上書きを拒否し、LiteRT-LM形式、Chat能力、SHA-256、HTTPSの取得URL、各トークン予算などを検査する。選択画面・モデルパス解決の基盤も既にある。

**ファイルピッカーを付けるだけでは完成しない。** 現在はローカルファイルだけの登録でもHTTPS URLが必須で、任意形式を受け付ける設計でもない。まず対応する `.litertlm` のみを対象にするなら、既存基盤の活用範囲は大きい。GGUF・safetensors等はファイル名を変えても動かず、別エンジンや変換・外部サーバー接続が必要になる。

私の実装案は次の順序。

1. 登録データへ取得元の区別（同梱・ダウンロード・ローカル取り込み）を追加し、ローカル取り込み時の不要なURL必須条件を整理する。ID、保存名、ハッシュ、能力、形式、エンジン、互換バージョンを保持する。
2. `YuiPickedFilePolicy` とWindows/Mac/iOS各ピッカーにモデル用の用途を追加する。既存の画像／アバター上限を流用しない。モバイルのアクセス権やファイル提供元も扱う。
3. ファイルを一時領域へストリームコピーし、空き容量・キャンセル・ハッシュを確認する。GB単位のモデルを丸ごとメモリへ読み込まない。保存とカタログ更新を原子的に行い、失敗時に標準モデルを壊さない。
4. 小さな試験入力でロード・会話の成功を確認し、登録後に選べるようにする。失敗したモデルは成功扱いしない。Chat専用モデルへSTT・画像の能力を勝手に付けない。標準E2Bの音声認識経路は維持する。
5. 削除時は参照中のモデルを確認し、モデル本体と実行キャッシュを区別する。重複保存を避け、失敗したコピー・ダウンロードの残骸に上限を設ける。

これは「最初に互換LiteRTモデルだけを扱う」場合の案。任意の人気モデルを広く使いたい要求なら、外部サーバー接続を先に整備する方が変更量を抑えやすい。初期実装を短くできる可能性はあるが、全形式・全モデル・全端末への対応が簡単とは判断しない。

## LM Studioと外部サーバーの接続案

現在の `backend/app/providers/lmstudio_chat.py` とProviderRouterは、既に設定URLへOpenAI互換の `/chat/completions` を送信する。モデルIDも設定できる。`litert_lm` も同じ実装を利用する。現状は非ストリーミング、HTTPタイムアウト90秒固定で、接続トークンの設定や各エンジン固有のオプションには未対応。

現行LM Studio接続の基本手順は、LM Studioで対応モデルをロードしてローカルサーバーを起動し、Backend Consoleの会話提供元をLM Studioにし、Base URLと実際のモデルIDを設定・保存する。その後短い会話で確認する。同じPCの通常例は `http://127.0.0.1:1234/v1`。アプリ／モバイルのBackend URLにはYui Backendのアドレスを入れ、LM Studioのポートを直接入れない。別端末の `127.0.0.1` はその端末自身である。[LM Studio公式の互換API説明](https://lmstudio.ai/docs/developer/openai-compat)。

私は既存LM Studio設定を維持しつつ、そのHTTP実装を「OpenAI互換ローカルサーバー」接続として共通化する案を推す。提供元ごとに接続例・既定値・能力の違いを表示し、Base URL、モデルID、必要時の認証、待ち時間を設定する。先にモデル一覧取得、短い会話、本文・エラー・文字コードの検証を実装し、ストリーミング・キャンセル・待機列は別の検討項目にする。

### 互換性の候補と優先順位（提案）

| 候補 | 想定する位置づけ | 接続方法・確認事項 |
| --- | --- | --- |
| LM Studio | 初心者向けの第一候補。GUIからモデルとサーバーを扱う現行導線を維持 | 通常 `127.0.0.1:1234/v1`。表示されたモデルIDを指定 |
| Ollama | 次に実機互換を確認する候補 | 通常 `127.0.0.1:11434/v1`。モデルタグを指定。OpenAI APIの対応範囲は部分的 |
| llama.cpp / llama-server | GGUFや細かな実行設定を使う利用者向け | サーバーの `/v1` とモデルID／aliasを指定。チャットテンプレートも確認 |
| vLLM | GPUサーバーで運用する利用者向け | OpenAI互換サーバーへ接続。Yuiにエンジンを同梱する要求とは分けて検討 |

これは利用率ランキングではなく、既存コードへの接続しやすさと用途に基づく私の優先順位。初心者の導線をLM Studio中心にする判断には賛成だが、「初心者にはLM Studioしかない」とは固定しない。OllamaもWindows/macOSの公式アプリにモデルの取得・会話GUIを備える。[Ollama公式アプリ](https://ollama.com/blog/new-app)、[Ollamaの互換API](https://docs.ollama.com/api/openai-compatibility)、[llama-server公式API](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)、[vLLM公式API](https://docs.vllm.ai/en/latest/serving/online_serving/openai_compatible_server/)。会話中の「Orama」はここではOllamaを想定している。別製品を指していた場合は再検討する。

同じAPI形式でも、system指示、thinking、出力予算、JSON、画像、ツール呼び出し、キャンセルの動作は一律ではない。互換性の宣言はエンジン・バージョン・モデルの組み合わせごとの試験結果に基づける。今回LM Studio実機やOllama、llama-server、vLLMを新規導入して比較したわけではない。

### 実装前に決めること

- 接続テストの成功条件と、未ロード・空本文・thinkingのみ・不正JSON・途中終了の扱い。今回、現行LM Studio接続が空本文や本文なし応答を成功扱いする共通不具合は修正し、回帰テストを追加した。
- コールドロードを含む待ち時間、キャンセル、連打、同時利用の待機列。パラメータ数だけでタイムアウトを決めない。
- モデル変更時に人格・記憶・会話履歴をどう引き継ぐか。能力不足のモデルでは音声・画像等を選択不可にするか別モデルへ分担するか。
- 認証を要求するサーバーへの接続と端末間の通信方式。現行アプリ用Backend APIには認証がないため、接続機能追加とインターネット公開を同一視しない。
- モバイル取り込みでの保存容量、実行時メモリ不足、バックグラウンド移行、発熱、ライセンス表示、失敗時の標準モデルへの復帰。

## CSV作業モードに対する評価（仕様変更ではない）

現在のBackend Consoleの作業は、CSVを分類別に件数・合計へ集計し、CSV・グラフ・HTMLを作る決定的な処理で、LLMを使用しない。今回3行の集計、再起動後の成果物表示、保存したCSVの値を確認した。**動作することは、製品として必要なことの証明ではない。**

私の判断は、現状のCSV専用機能を主機能として拡張する優先度は低い。既存の表計算ソフトで代替でき、キャラクター対話とのつながりも薄い。実験機能として導線を控えめにし、利用率・繰り返し利用・利用者が解決したい問題を確認する。まず会話、音声入力、モデル選択、アバター、端末間接続の安定性を優先したい。

将来「キャラクターに資料を渡し、会話しながら確認・分析する」体験につなげるなら、CSV集計は確実な計算を行う道具として価値がある。その場合も、LLMが説明し、集計値は検証可能な処理で求める形が望ましい。現時点で需要の証拠はなく、CSV機能の削除・仕様変更は今回行っていない。実験として残すか削るかは、想定利用者と実測を見て改めて決める。
